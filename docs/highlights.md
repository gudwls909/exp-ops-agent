## 0. 1분 소개

> 박사 과정에서 Voyager 기반 실험을 큐로 수십 개씩 돌렸는데, 학습이 끝나고 종료하다 멈추는 job이 계속 생겼습니다.
> 그래서 "로그가 120초 안 바뀌면 kill -9" 하는 감시 스크립트를 만들어 썼는데, 이건 아는 장애 하나만 잡고, 느린 job과 멈춘 job을 구분하지 못하고, 왜 멈췄는지는 알려 주지 않았습니다.
>
> 이 스크립트를 베이스라인으로 두고, 같은 문제를 LLM Agent로 풀었습니다. Agent는 MCP 도구로 로그·설정·체크포인트를 **읽기만** 하고, 진단과 수정 제안을 보고서로 냅니다. 실행은 사람이 승인해야 일어납니다.
>
> 평가는 실제 GPU에서 장애를 일부러 일으키는 시뮬레이터로 했습니다. 처음 보는 조건에서 규칙은 느린 정상 job을 죽이거나 장애를 전부 놓쳤고, Agent는 잘못 죽인 게 0건, 놓친 게 0건이었습니다. 설정이 원인인 장애는 6개 모두 실험 의미를 바꾸지 않고 고쳤습니다.
> 마지막으로 결과가 확인된 조치만 기억하게 했더니, 재시작으로는 안 풀리는 장애를 첫 시도에 푼 비율이 0/14에서 12/14가 됐습니다.
>
> 이 과정에서 실패하거나 규칙보다 못했던 순간이 24번 있었고, 오늘은 그중 몇 개를 어떻게 풀었는지 말씀드리겠습니다.

## 1. "Agent가 틀리면 모델보다 도구를 먼저 의심한다" (4 → 5 → 13)

**상황.** 첫 평가에서 Agent가 규칙과 동점이었습니다. 놓친 장애 수가 같았고, 규칙은 비용이 0원이었습니다.

**원인 찾기.** 틀린 job의 보고서 근거를 읽었습니다. NaN job에 대해 "로그 0.7초 전 갱신, 정상 진행"이라고 썼더군요. **로그를 열어 보지도 않았습니다.** 요약 도구가 주는 정보에 loss가 없었기 때문에, 요약만 보면 NaN job은 완벽하게 정상이었습니다.

**해결 → 그런데 회귀.** 요약에 마지막 loss를 넣자 NaN은 3/3으로 잡았는데, 이번엔 hang을 0/3으로 놓쳤습니다. 멈춘 job도 **멈추기 직전 줄**의 loss는 정상이니까, 그 숫자를 믿고 "26초 전 갱신, 정상"이라고 본 겁니다. 26초가 긴지 짧은지 판단할 기준이 없었습니다.

**두 번째 해결.** "이 job의 평소 로그 간격 대비 몇 배 조용한가"를 요약에 넣었습니다. 1초마다 찍던 job이 26초 조용하면 26배, 20초마다 찍던 job이 15초 조용하면 0.75배. 이후 감지 24/24, 그리고 Agent가 로그를 덜 열어 봐도 돼서 **비용이 46% 줄었습니다.**

**같은 교훈이 또.** 나중에 발산한 job을 고칠 때, Agent가 lr은 맞게 낮췄는데 이미 망가진 체크포인트에서 재시작했습니다. 근거를 보니 "step 150의 loss 0.025 — 정상"이었습니다. 그런데 step N 로그의 loss는 업데이트 **전** 값이고, 체크포인트 N은 업데이트 **후** 가중치입니다. **Agent의 추론은 도구가 준 정보로는 맞았고, 도구가 오해를 부르는 정보를 줬습니다.** 도구를 고치자 해결됐습니다.

**한 줄.** Agent 정확도 문제의 상당수는 프롬프트가 아니라 도구가 무엇을, 어떤 형태로 보여 주느냐에서 옵니다.

## 2. "하지 마라고 부탁하지 않고, 할 수 없게 만든다" (6 → 15 → 21)

**① 말과 행동이 달랐다.** 처음엔 승인 요청을 도구로 줬습니다. 그랬더니 보고서에는 "terminate 요청함"이라고 써 놓고 도구는 안 부른 경우가 나왔습니다. 평가를 보고서가 아니라 **실제 승인 대기열**로 채점하게 해 둔 덕분에 발견했습니다.
→ 요청 도구를 없애고, 보고서에 쓴 조치를 **코드가** 대기열에 넣게 바꿨습니다. 구조적으로 어긋날 수 없게.

**② 프롬프트를 지키지 않았다.** OOM이 나면 "실질 batch는 유지하고 grad_accum을 늘려라. batch를 줄이면 실험 의미가 바뀐다"고 정책에 썼습니다. 그런데 7번 중 3번은 batch를 줄였습니다. 그중엔 근거에 "batch 유지를 위해…"라고 쓰고 1000분의 1로 줄인 제안도 있었습니다. 이걸 사람이 승인했다면 job은 끝까지 돌았을 겁니다 — 즉 "수정 성공률"만 재면 **성공으로 채점됩니다.**
→ batch 계열 설정을 **바꿀 수 있는 목록에서 뺐습니다.** 그리고 평가에 "실험 의미 보존" 지표를 따로 만들었습니다.

**③ 기억은 있었는데 쓰지 않았다.** 메모리에 "같은 설정 재시작: 실패 3, 성공 0"이 쌓였는데도 Agent는 또 같은 설정으로 재시작했습니다. 정책에 "처음 멈춘 job은 같은 설정으로 재시작"이라는 문장이 있었고, **명시적인 정책이 메모리를 이겼습니다.**
→ 반복 실패한 조치를 검증 단계에서 거부하고, 성공 기록이 있는 방법을 알려 주게 했습니다.

**한 줄.** LLM의 확률적 실수가 반복해서 보이면 프롬프트 튜닝을 멈추고 규칙을 코드로 옮깁니다. **Agent는 무엇을 고칠지 판단하고, 그 판단이 안전한 범위 안에 있는지는 코드가 보장합니다.**

## 3. "평가 숫자를 믿기 전에 평가를 의심한다" (7, 8, 20, 22, 24)

**① 베이스라인이 불리했다.** 규칙이 이미 끝난 job 3개를 "멈춤"으로 오판했습니다. 원인은 평가 스크립트가 끝난 자식 프로세스를 회수하지 않아 좀비가 생긴 것. 실제 서버 조건으로 맞추자 규칙의 오판은 0이 됐습니다. **베이스라인에 불리한 버그를 두고 이기면 의미가 없습니다.**

**② 좋은 숫자가 가짜였다.** 메모리 실험 1차 결과는 "해결 3/6 → 6/6"로 발표하기 좋은 숫자였습니다. 그런데 저장된 runbook을 열어 보니 OOM 수정이 "성공 0, 실패 3"으로 기록돼 있었습니다. 실제로는 끝까지 돈 수정이었습니다. 결과 판정(critic)이 "grad_accum을 늘려 느려진 job"을 "다시 멈춤"으로 오판한 겁니다. Voyager에서도 critic이 틀리면 잘못된 skill이 쌓이는 것과 같습니다. **좋아 보이는 숫자일수록 저장된 내용을 직접 열어 봅니다.**

**③ 표본이 작으면 결론을 내리지 않는다.** critic을 고친 뒤 에피소드 3개로는 "on이 빠름 1, 같음 1, 느림 1", 신뢰구간이 0을 포함했습니다. 새 seed 2개 × 8 에피소드로 늘려 같은 장애끼리 짝을 지어 비교하자 평균 +1.06라운드, 95% CI [+0.62, +1.44]로 0에서 떨어졌습니다. 그리고 **효과가 없는 조건(OOM, 차이 0)도 같이 보고합니다.** 논문에서 seed 3개로 1점 차이를 주장하지 않는 것과 같은 기준입니다.

**한 줄.** 평가 파이프라인도 코드이고 버그가 있습니다. 숫자가 이상하면 — 특히 좋으면 — 평가부터 봅니다.

## 4. "사람 승인이 들어간 시스템은 시간이 흐른다" (17, 10, 23)

**① 승인한 것과 실행된 것이 달랐다.** 평가 도중 승인 실행 단계에서 프로그램이 죽었습니다. 재시작 요청에는 "마지막 체크포인트부터"라고만 적혀 있었는데, **승인을 기다리는 동안** 발산 중인 job이 새 체크포인트(이미 망가진 것)를 썼고, 실행 시점의 "마지막"이 그걸 가리켰습니다.
→ 승인 대상을 의도가 아니라 **구체적인 step**으로 고정하고, 실행 직전에 다시 검증해서 실패하면 프로그램이 죽지 않고 "실패"와 이유를 남기게 했습니다. 확인 시점과 사용 시점이 다른 TOCTOU 문제입니다.

**② 사람 승인이 실제로 막았다.** 앞의 "batch 1000분의 1" 제안은 데모에서 사람이 변경 내용을 보고 거절했습니다. 자동 적용이었다면 실험이 조용히 바뀌었을 겁니다. 승인 화면에 "무엇을 왜 바꾸는지"가 보여야 하는 이유입니다.

**③ 장애를 고치는 도구가 장애를 만들 뻔했다.** 큰 평가를 돌리다 서버 디스크 100GB를 채웠습니다. "망가지기 전으로 되돌아가기" 때문에 체크포인트를 전부 남겼는데 보관 정책이 없었습니다. "최근 5개 + 일정 간격 이정표"만 남기게 바꿨습니다. 최근 것만 남기면 오래전에 망가진 job은 돌아갈 곳이 없기 때문입니다. 운영 Agent라면 **자기 자신의 자원 사용**도 감시 대상입니다.

## 예상 질문과 답

**Q. 규칙으로도 되는 거 아닌가요? NaN도 `grep nan` 하면 잡히잖아요.**
맞습니다. 아는 장애는 규칙이 더 싸고 빠르고 확실합니다. 문제는 규칙은 **미리 예상한 장애만** 잡고, 새 장애마다 사람이 규칙을 추가해야 한다는 점입니다. 그리고 "느린 job vs 멈춘 job"처럼 threshold 하나로 둘 다 잘할 수 없는 경우가 있습니다(held-out에서 규칙은 10~30초면 false kill 3/15, 60초면 놓침 12/12). 실무라면 규칙으로 1차 필터 → 의심 job만 Agent로 보내는 혼합 구조가 맞다고 봅니다. 비용도 그만큼 줄어듭니다.

**Q. LLM이 위험한 조치를 하면요?**
Agent에게는 읽기 도구만 있습니다. 실행은 사람 승인 후에만, 그리고 승인 전후로 코드가 검증합니다: 바꿀 수 있는 설정 목록과 범위, 망가진 체크포인트 거부, 근거 대조, 반복 실패 거부, pid 재사용 방어, SIGTERM 먼저. 이 약속들은 테스트 48개로 고정했고, 누가 실행 도구를 추가하면 테스트가 깨집니다.

**Q. LLM은 매번 답이 다른데 어떻게 평가했나요?**
같은 조건을 반복(2~3회, 메모리는 16쌍)하고, 개발 중 본 시나리오(dev)와 보지 않은 시나리오(held-out)를 나눴습니다. held-out은 결과를 보고 Agent를 고치지 않는다는 규칙을 먼저 정했습니다. 채점은 말(보고서)이 아니라 행동(실제 요청)과 결과(재시작한 job이 끝까지 돌았나)로 했습니다.

**Q. 왜 LangChain 같은 프레임워크를 안 썼나요?**
루프 자체는 수십 줄이고, 이 프로젝트에서 중요한 건 루프가 아니라 도구 설계·검증·평가였습니다. 직접 짜서 메시지 구조, tool_call_id, 재시도, 비용 계량을 전부 통제했고, 그래서 "보고서와 행동 불일치" 같은 문제를 구조로 막을 수 있었습니다. 프레임워크는 필요해지면 그 위에 얹으면 됩니다.

**Q. 비용은요?**
순찰 1회 $0.01~0.03(gpt-5-mini). 요약 도구를 개선했을 때 정확도와 비용이 같이 좋아졌고(−46%), 메모리를 쓰자 에피소드당 비용이 −39%였습니다. 실서비스라면 규칙 1차 필터로 Agent 호출 자체를 줄이겠습니다.

**Q. 실제 환경에서는요?**
가장 큰 한계입니다. 장애 유형과 로그 형식을 직접 설계했습니다. 다음 단계는 실제 연구 로그를 재생하는 평가이고, 남은 실패 유형(살아 있는데 오래 조용한 job을 정상으로 보고)은 코드 일관성 검사로 막고 새 held-out으로 재려고 합니다.

**Q. 연구 경험과 어떻게 연결되나요?**
runbook 메모리는 제 연구 주제였던 Voyager의 skill library와 같은 원리입니다 — 실행해서 검증된 것만 저장하고 비슷한 상황에서 꺼내 씁니다. 연구에서 ablation과 baseline 비교를 하던 방식 그대로, 메모리 on/off를 같은 장애끼리 짝지어 비교했고, critic 오류가 skill library를 오염시키는 문제를 실제로 겪고 고쳤습니다.

## 발표 시간별 구성

- **3분**: 1분 소개 + 이야기 2 (구조로 막기)
- **10분**: 1분 소개 + 구조도 + 이야기 1, 2, 3 + 결과 표 3개
- **20분 이상**: 위 + 이야기 4 + 데모(장애 job 띄우기 → 순찰 → 승인 → 재시작 완료) + 한계
