# 문제 해결 기록

개발하면서 **실패했거나, 규칙 베이스라인보다 못하거나 같았던 순간**을 기록한다.
각 항목: 상황 → 증상(숫자) → 원인을 찾은 방법 → 해결 → 결과 → 교훈.
발표·면접에서 "이런 문제가 있었고, 이렇게 원인을 찾았고, 이렇게 해결했다"로 바로 쓸 수 있게 쓴다.

---

## 1. 실패 주입이 너무 티가 났다 (시뮬레이터)

- **상황**: OOM 실패를 "GPU 메모리를 1GiB씩 계속 잡는 반복문"으로 만들었다.
- **증상**: OOM traceback 마지막 줄에 `hog.append(torch.empty(...))`가 그대로 찍혔다.
- **원인**: 실패를 일으키는 코드 자체가 로그에 노출됨. Agent가 원인을 추론하지 않고 코드를 읽고 맞힐 수 있다 → 평가가 쉬워짐.
- **해결**: 실제로 흔한 원인으로 바꿨다. OOM은 "커리큘럼 설정 실수로 batch size 급증", NaN은 "lr 스케줄러 설정 실수", crash는 "손상된 데이터 shard".
- **결과**: traceback이 실제 학습 코드와 같은 모양(`F.linear` 안에서 OOM)이 됐다.
- **교훈**: 평가용 시뮬레이터는 **정답이 새는 경로**를 막아야 한다. 같은 이유로 job id도 `run-7cc9`처럼 랜덤으로 붙이고(이름이 `hang1`이면 이름으로 맞힘), 실행 명령(`--fail hang`)은 Agent에게 보여 주지 않는다.

## 2. 규칙 베이스라인의 한계를 직접 재현 (false kill)

- **상황**: 기존에 쓰던 `vb_hang_killer.sh`(로그가 120초 안 바뀌면 kill -9)를 Python 규칙으로 옮겨 베이스라인으로 만들었다.
- **증상**: "느리지만 정상"인 job(로그 간격 20초)이 threshold 15초에서 **가끔 HANG**으로 판정됨.
- **원인**: 확인하는 순간이 로그를 쓴 뒤 15~20초 사이면 HANG. 확인 시점의 약 25%. 60초마다 확인하는 스크립트는 결국 언젠가 죽인다.
- **해결 방향**: threshold를 올리면 진짜 hang 감지가 늦어지고, 더 느린 job은 또 걸린다 → threshold 하나로는 "빨리 찾기"와 "잘못 안 죽이기"를 동시에 못 함. Agent가 로그 내용(step 증가, loss 감소)을 보고 판단하게 했다.
- **교훈**: 절대 시간 규칙은 job마다 속도가 다른 환경에서 trade-off를 피할 수 없다.

## 3. 테스트가 잡은 버그: 종료를 너무 일찍 보고

- **상황**: 승인 후 `terminate`가 "SIGTERM으로 정상 종료"라고 보고했다.
- **증상**: 안전장치 테스트에서 보고 직후 프로세스가 **아직 살아 있었다** (19개 중 1개 실패).
- **원인**: 종료 중인 프로세스는 `/proc/<pid>/cmdline`이 먼저 비워진다. pid 재사용 방어용으로 "명령줄에 job_id가 있나"를 확인하는 `is_alive`가 그 순간 "죽었다"고 판단함.
- **해결**: 종료를 기다릴 때는 "프로세스가 완전히 사라졌나"(좀비 포함)로 따로 확인.
- **결과**: 3회 반복 19/19 통과.
- **교훈**: 실제 학습 job이었다면 **체크포인트 저장 중에** "끝났다"고 보고하고 바로 재시작해서 체크포인트가 깨질 수 있었다. 안전 기능일수록 테스트가 먼저 있어야 한다.

## 4. 평가 첫 결과: Agent가 규칙과 동점 + NaN을 놓침

- **상황**: 실패 8종 job을 띄우고 Agent vs 규칙 비교.
- **증상**: 놓친 장애 Agent 1/3, 규칙(10~15s) 1/3로 **동점**. 규칙은 비용 0원. Agent는 NaN job을 `healthy`로 진단.
- **원인 분석**: 보고서의 근거를 읽음 → "log_age 0.7s, last_step 300/3000 — 정상 진행". **로그를 열어 보지 않았다.** 요약 도구(`list_jobs`)에 loss가 없어서 NaN job이 요약으로는 완벽히 정상이었다. 실제 로그에는 `loss nan` 84줄.
- **해결**: 프롬프트로 "모든 로그를 열어라"(비용이 job 수만큼 증가) 대신, **요약 도구에 `last_loss`, `last_step_time_s` 추가** (거의 공짜).
- **결과**: NaN 0/3 → 3/3, slow 진단도 3/3.
- **교훈**: Agent의 정확도 문제는 프롬프트보다 **도구가 무엇을 보여 주느냐**에서 오는 경우가 많다.

## 5. 고쳤더니 다른 곳이 망가짐 (hang 회귀)

- **상황**: 4번 수정 후 다시 3회 평가.
- **증상**: hang 진단 1/1 → **0/3** (`healthy`). 전체 놓침 5/9로 규칙(3/9)보다 나빠짐.
- **원인 분석**: 근거를 읽음 → "최근 로그(약 26s 전) 업데이트, loss 0.281, step_time 0.1s로 정상". 두 가지 문제:
  1. 26초가 긴지 모른다. 이 job은 원래 1초마다 로그를 쓰므로 26배 지연인데, 요약에 "평소 간격"이 없음.
  2. 새로 넣은 `last_loss`는 **멈추기 직전 줄**의 값이라 hang job도 정상으로 보인다. 요약을 믿고 로그를 덜 열어 봄 (도구 호출 11회 → 6~13회).
- **해결**: 요약에 `recent_log_interval_s`(최근 로그 간격 중앙값)와 `log_age_vs_interval`(평소 대비 배수) 추가. 프롬프트에 "절대 시간이 아니라 배수로 판단", "마지막 줄의 값이 정상이어도 진행 중이라는 뜻은 아니다" 명시.
- **결과**: hang 0/3 → 3/3. 전체 진단 24/24, 놓침 0/9, false kill 0/15. 순찰당 비용 $0.0206 → $0.0111 (−46%), 65s → 45s.
- **공정성**: 같은 "평소 간격 대비 배수" 신호를 규칙에도 줘서(규칙 B) 비교 → 규칙 B도 NaN 3/9를 놓침. Agent만 좋은 신호를 받아서 이긴 게 아님을 확인.
- **교훈**: 한 곳을 고치면 반드시 **전체 회귀 평가**. 정보를 더 주면 LLM이 그 정보를 과신할 수 있다.

## 6. 보고서와 실제 행동이 다름 (say-do gap)

- **상황**: Agent가 `request_action` 도구로 승인 요청을 보내게 했다.
- **증상**: 보고서에는 NaN job에 `action_requested: terminate`라고 썼는데, 승인 대기열에는 요청이 없음 (3회 중 1회).
- **찾은 방법**: 평가를 보고서가 아니라 **승인 대기열에 실제로 들어간 요청**으로 채점하도록 처음부터 설계해 둠. 보고서만 채점했으면 못 잡았다.
- **해결**: 프롬프트로 "도구를 꼭 불러라"가 아니라 **구조로**: `request_action` 도구를 없애고, 보고서의 조치를 코드가 승인 대기열에 넣는다. 지어낸 job_id는 거부.
- **결과**: 말과 행동 불일치 0 (구조적으로 불가능). 테스트로 고정.
- **교훈**: LLM의 확률적 행동에 기대지 말고 구조로 막는다. (kill 도구를 아예 주지 않은 것과 같은 원칙)

## 7. 평가 코드 버그 ① — 베이스라인이 불리했다 (좀비 프로세스)

- **증상**: 첫 평가에서 규칙이 false kill 3/5. 대상은 이미 끝난 job(oom, crash, finished).
- **원인**: 평가 스크립트가 job의 부모 프로세스인데 끝난 job을 회수하지 않아 **좀비**가 됨. 규칙은 `os.kill(pid, 0)`만 보므로 좀비를 "살아 있음"으로 판단.
- **해결**: 실제 서버(큐 스크립트가 회수)와 같은 조건으로 평가 환경을 맞춤.
- **결과**: 규칙 false kill 3/5 → 0/5.
- **교훈**: 베이스라인에 불리한 버그를 두고 이기면 의미 없다. **비교는 공정해야 한다.** 숫자가 이상하면 평가 코드부터 의심.

## 8. 평가 코드 버그 ② — 반복 평가 2회차부터 결과 누락

- **증상**: 3회 평가에서 2, 3회차 진단이 전부 "(누락)".
- **찾은 방법**: Agent가 보고한 job id 목록을 회차별로 출력 → 2, 3회차에도 **1회차 job id**를 보고하고 있었다.
- **원인**: MCP 서버 설정을 모듈 import 시점에 만들어서, 그때의 환경변수(1회차 폴더 경로)가 고정됨.
- **해결**: 실행할 때마다 서버 설정을 새로 만든다.
- **교훈**: "(누락)"이 한꺼번에 나온 패턴 → 모델 문제가 아니라 파이프라인 문제라는 신호.

## 9. Held-out 평가: 개발 때 안 본 조건에서도 통하나

- **상황**: 4~6번은 같은 8개 시나리오를 보고 고친 결과라 "시험 문제를 보고 공부한 점수"일 수 있다. 개발 중 한 번도 돌리지 않은 조건 9개(대기 60초, step 속도 0.03/0.3초, 로그 빈도 5 step, 실패 시점 10~500, slow 50배, hang 2개)를 만들어 **한 번만** 돌렸다. 결과를 보고 고치지 않는다는 규칙을 먼저 정함.
- **결과 (3회)**: Agent false kill 0/15, 놓침 0/12, 진단 25/27, 순찰당 $0.017. 규칙 A(10~30초)와 규칙 B는 **false kill 3/15** (50배 느려진 정상 job을 3회 모두 종료 판정) + NaN 놓침 3/12. 규칙 A(60초)는 false kill은 0이지만 **장애를 전부 놓침**(12/12).
- **Agent가 틀린 2개**: 50배 느려진 job을 `healthy`로 진단(조치는 맞음, 종료 요청 안 함). 근거를 보면 확인 시점이 마침 느린 로그 한 줄이 막 찍힌 직후(log_age 0.6초)라 "로그가 활발히 갱신됨"으로 판단하고, 요약에 있던 `last_step_time_s 5.00`(평소 0.1초)을 놓쳤다. 맞힌 1회는 "step_time이 0.1→5.00s로 증가"를 근거로 들었다.
- **조치**: held-out이므로 **고치지 않고 기록만** 한다. 고친다면 "step_time이 평소보다 크게 늘면 slow로 분류" 기준을 프롬프트에 넣는 것 → 그 뒤에는 새 held-out이 필요.
- **교훈**: dev 점수(24/24)가 held-out(25/27)에서도 거의 유지됐다 → 과적합은 크지 않다. 규칙의 약점(false kill과 놓침의 trade-off)은 조건이 다양해지자 **dev보다 더 뚜렷하게** 드러났다.

## 10. "고치긴 고쳤는데 실험을 바꿔 버린" 수정 제안 (OOM)

- **상황**: 실패가 설정에서 자연스럽게 생기도록 시뮬레이터를 바꾸고(커리큘럼 2단계 batch 1,048,576 → 진짜 CUDA OOM), Agent가 "설정을 고친 재시작"을 제안하게 했다. 정책: "실질 batch는 유지하고 grad_accum을 늘려라. batch 자체를 줄이면 실험 의미가 바뀐다".
- **증상**: Agent 제안 = `stage2_batch: 1,048,576 → 1,024` (1000배 축소). 근거에는 "효과적 batch 유지 위해 grad_accum은 그대로 둠"이라고 썼다 → **근거와 제안이 서로 모순**. 이대로 승인했으면 job은 끝까지 돌았을 것이다.
- **찾은 방법**: 승인 대기열에서 사람이 변경 내용을 보고 거절. (`grad_accum 4`로 하면 메모리 609MiB로 같은 실질 batch가 돈다는 건 미리 측정해 둠)
- **원인**: "job이 다시 돌게 만드는 것"이 가장 쉬운 해결이고, LLM은 정책 문장보다 쉬운 해결을 택했다.
- **교훈 / 다음 조치**:
  - "수정 후 job이 끝까지 돌았나(수정 성공률)"만 재면 이 제안은 **성공으로 채점된다**. 평가에 "실험 의미 보존" 지표가 필요하다 (예: 실질 batch = batch × grad_accum이 바뀌었나, lr이 원래 의도 범위인가).
  - 검증 코드에서도 막을 수 있다: batch 계열을 바꾸는 제안은 실질 batch가 유지될 때만 허용, 아니면 "실험 변경"으로 표시하고 경고.
  - 사람 승인 단계가 실제로 필요하다는 근거 (자동 적용이었다면 실험이 조용히 바뀌었다).

## 11. 시나리오 설계 실수: 순찰 전에 이미 끝나 버린 발산 job

- **상황**: 2단계에서 lr 1e3으로 loss가 발산하는 job(300 step)을 띄우고 35초 뒤 순찰.
- **증상**: Agent 진단 `finished` ("Exit 0, 마지막 loss 8.8e+31, 결과 검토 권장"). 재시작 제안 없음.
- **원인**: 300 step × 0.1초 = 30초라 **순찰 전에 학습이 끝났다** (시나리오 타이밍 실수). 그리고 정책에 "끝났지만 결과가 망가진 job"이라는 경우가 없었다 (nan_loss는 "계속 돌고 있음"으로 정의).
- **교훈 / 다음 조치**: 진단 상태는 맞았다(정말로 끝났으니까). 하지만 실무에서 더 흔한 건 "밤새 돌고 아침에 보니 끝났는데 loss가 망가짐"이다 → `finished_but_diverged` 같은 진단과 "발산 전 체크포인트부터 lr 낮춰 재학습" 제안이 필요. 평가 시나리오에도 이 경우를 일부러 넣는다.

## 12. 설정 기반 수정이 실제로 동작함 (성공 사례)

- **결과 (1회 데모)**: 손상된 데이터 shard로 죽은 job → Agent가 `data_shards`에서 3번 제외 + "사람 확인 필요" 제안 → 승인 → step 100부터 재시작, shard-0003을 다시 읽지 않고 300/300 완료. hang job → 같은 설정 재시작 제안 → 승인 → SIGTERM으로 step 70 체크포인트 저장 → 재시작 → 300/300 완료.
- **안전장치**: 바꿀 수 있는 설정은 허용 목록 + 범위로 제한 (`steps`, `seed` 같은 실험 정체 설정은 불가, lr ≤ 1, shard는 빼기만 가능, 없는 체크포인트 거부). 거부된 제안은 사람에게 가지도 않는다. 테스트 10개로 고정.

## 13. 수정 평가: Agent 6/8 vs 그냥 재시작 2/8 — 남은 실패는 "내 도구가 준 잘못된 단서"

- **상황**: 설정 때문에 생긴 실패 4종(lr 발산, OOM, 손상 shard, hang)에 대해 "수정 후 끝까지 정상 완료 + 실험 의미 보존"을 채점. 제안은 사람이 **검토 없이 전부 승인**했다고 가정(제안 품질 자체를 보기 위해).
- **결과 (2회)**:

  | | 좋은 수정 (성공 + 의미 보존) | 비고 |
  |---|---|---|
  | Agent | **6/8** | OOM은 이번엔 `grad_accum 4`로 실질 batch 유지 (10번과 달리 2/2), shard 3만 제외, hang은 변경 없이 |
  | 그냥 재시작 | 2/8 | hang만 성공. OOM·shard는 같은 자리에서 다시 죽고, 발산은 망가진 체크포인트에서 계속 폭주 |

- **Agent가 틀린 2개 (발산)**: lr을 1e3 → 1e-3으로 맞게 낮췄는데 **step 150 체크포인트**부터 재시작 → 마지막 loss 4e+21로 실패.
- **원인 분석**: Agent 근거 = "마지막 정상 체크포인트는 step 150 (loss 0.02497)". `list_checkpoints`가 준 "step 150에서 찍힌 loss"를 믿었다. 그런데 **step N 로그의 loss는 업데이트 전 값이고, 체크포인트 N은 업데이트 후 가중치**다. 2단계는 step 150에서 시작해 lr 1e3으로 한 번 업데이트한 뒤 저장 → 체크포인트 150은 이미 망가져 있었다. **Agent의 추론은 도구가 준 정보로는 맞았고, 도구가 오해를 부르는 정보를 줬다.**
- **해결**: `list_checkpoints`가 체크포인트마다 `loss_at_next_log`(그 가중치에서 출발한 다음 로그의 loss)를 같이 주고, 도구 설명에 "가중치가 멀쩡한지는 다음 로그의 loss로 판단하라"고 명시.
- **교훈**: 4·5번과 같은 결론이 또 나왔다. Agent의 실패 원인을 찾을 때 **모델보다 먼저 도구가 준 정보가 정확했는지** 본다. ⚠️ 이 수정은 같은 시나리오를 보고 고친 것이므로 수정 평가에도 held-out이 필요하다.

## 14. 하나 고치니 또 다른 곳이: 검증기가 조용히 버린 OOM 수정

- **상황**: 13번 수정(체크포인트 도구) 후 Agent만 2회 재평가.
- **증상**: 발산 0/2 → **2/2** (이번엔 step 100부터). 그런데 OOM 2/2 → **0/2** ("제안 없음"으로 채점). 합계는 6/8 그대로.
- **원인 분석**: 보고서에는 OOM에 `restart, grad_accum 2048`이 **있었다**. 근거: "실질 배치 크기는 유지하되 grad_accum을 524288/256=2048로". 방향은 맞다(실질 batch 유지). 그런데 허용 범위가 `grad_accum ≤ 1024`라 검증기가 거부했고, **거부된 제안은 아무 피드백 없이 버려져** 사람에게도 가지 않았다.
- **해결**: 보고서를 대기열에 넣기 전에 검증만 먼저 해 보고, 거부된 제안이 있으면 **거부 이유를 Agent에게 돌려줘서 한 번 고쳐 쓰게** 했다 (최대 1회). 검증 실패 이유가 구체적이어야 고칠 수 있으므로 테스트로 고정.
- **교훈**: 안전장치(검증기)가 막기만 하고 이유를 안 알려 주면, 안전하긴 해도 **쓸모 있는 제안까지 사라진다**. 사람 조직에서 "반려 사유 없는 반려"와 같다. 그리고 허용 범위(1024) 자체도 내가 임의로 정한 값이라 근거가 약했다.

## 15. 프롬프트로 고치기를 멈추고, 실험 의미 보존을 코드로 강제

- **상황**: 14번 수정(검증 실패 이유를 돌려주고 한 번 고쳐 쓰게) 후 재평가.
- **증상**: 좋은 수정 6/8 → **5/8**. OOM은 고쳐 쓰라고 하자 **batch를 줄이는 쪽으로** 바꿨다 (`stage2_batch 262144 + grad_accum 1024`, `stage2_batch 1024`) → job은 끝까지 돌았지만(수정 성공 2/2) 의미 보존 0/2. 발산은 다시 1번이 망가진 체크포인트(150)를 골랐다.
- **원인 분석**: 같은 시나리오에서 같은 종류의 실수가 회차마다 나왔다 사라졌다 한다. 지금까지 OOM 제안 7번(데모 1, 평가 6) 중 batch를 줄인 게 3번. **프롬프트에 "batch를 줄이지 마라"를 써 두는 것으로는 확률을 낮출 뿐 막지 못한다.** n=2짜리 재평가를 반복하며 프롬프트를 고치는 건 노이즈를 쫓는 일이 되고 있었다.
- **해결 (구조로)**:
  - `batch_size`, `stage2_batch`를 **바꿀 수 있는 설정 목록에서 제거**. 메모리 문제는 `grad_accum`으로만 풀 수 있다 (`grad_accum ≤ batch` 검사).
  - **망가진 체크포인트에서의 재시작을 검증기가 거부**: 체크포인트 다음 로그의 loss가 nan/inf이거나 그 전 최저 loss의 100배를 넘으면 "더 이른 step을 지정하라"는 이유와 함께 거부. `resume_from`을 안 정하면 마지막 체크포인트로 같은 검사.
  - 둘 다 테스트로 고정 (38개).
- **교훈**: 6번(말과 행동 불일치)과 같은 원칙. **LLM에게 "하지 마라"고 부탁하는 대신, 할 수 없게 만든다.** 확률적 행동이 반복해서 보이면 프롬프트 튜닝을 멈추고 규칙을 코드로 옮길 때다. Agent는 "무엇을 고칠지" 판단하고, 그 판단이 안전한 범위 안에 있는지는 코드가 보장한다.

## 16. 남은 1개: 다른 job의 진단을 베껴 씀 (job 간 혼동)

- **상황**: 15번(규칙을 코드로) 후 Agent만 2회 재평가.
- **결과**: 좋은 수정 **7/8** (발산 2/2 — 이번엔 둘 다 step 100, OOM 1/2, shard 2/2, hang 2/2). 정상 job 건드림 0.
- **남은 실패 분석**: OOM job에 `data_shards에서 3번 제외`를 제안. 근거에 "KeyError ... shard-0003.tar"라고 썼는데, 그 job의 실제 로그에는 **KeyError가 0줄이고 OutOfMemoryError만 2줄** 있었다. 같은 순찰에서 본 **다른 job(손상 shard)의 진단을 이 job에 그대로 붙였다**. job 5개를 한 대화에서 처리하면서 생긴 혼동.
- **왜 검증기가 못 막았나**: "shard를 빼는 것"은 허용된 변경이라 형식상으로는 통과. 검증기는 "제안이 안전한가"만 보고 "제안이 이 job의 증거와 맞나"는 안 본다.
- **고칠 방향 (아직 안 함, 다음 단계)**:
  - **근거 대조(grounding check)**: 보고서 evidence에 인용한 오류 문구가 그 job의 로그에 실제로 있는지 코드로 확인 → 없으면 거부 사유로 돌려준다.
  - 또는 이상한 job은 **job마다 따로** 진단(컨텍스트 분리). 비용은 늘어난다.
- **결정**: 같은 dev 시나리오에서 네 번째 수정은 하지 않는다. 지금 점수(7/8)를 dev 결과로 기록하고, 다음 수정은 held-out 수정 평가를 만든 뒤에 한다.

## 17. 승인을 기다리는 동안 상황이 바뀌었다 (승인한 것 ≠ 실행되는 것)

- **상황**: 수정 held-out 평가 1회차의 "그냥 재시작" 단계에서 평가 프로그램 전체가 예외로 죽었다.
- **증상**: `ValueError: step 1080 체크포인트 다음 loss가 6.1e+30 → 이미 망가진 체크포인트`가 **승인 실행 중**(`approvals.decide`)에 발생.
- **원인 분석**: 재시작 요청에 "마지막 체크포인트부터"라고만 적혀 있었다. 요청할 때의 마지막 체크포인트는 아직 판단할 수 없는 상태라 통과했다. 그런데 승인을 기다리는 동안 발산 중인 job이 계속 돌면서 **새 체크포인트(망가진 것)**를 썼고, 실행할 때의 "마지막"은 그 망가진 체크포인트를 가리켰다. 실행 직전 재검증이 이를 막은 건 맞지만, 예외를 처리하지 않아 프로그램이 죽었다.
- **해결**:
  - 요청할 때 "마지막 체크포인트"를 **구체적인 step으로 고정**한다 → 사람이 승인한 계획 그대로 실행된다.
  - 실행 직전 재검증에서 실패하면 프로그램이 죽지 않고 `failed` 상태와 이유를 남긴다.
  - 테스트로 고정 (41개).
- **교훈**: 사람 승인이 들어간 시스템에서는 **요청과 실행 사이에 시간이 흐른다**. 승인 대상은 "의도"가 아니라 구체적인 계획이어야 하고, 실행 직전에 다시 확인해야 한다 (TOCTOU 문제). Agent가 아니라 시스템 설계의 버그였고, 평가를 실제로 돌려 봤기 때문에 발견했다.

## 18. 시뮬레이터가 현실을 잘못 흉내 냄: 재시작해도 다시 멈추는 hang

- **상황**: 17번 수정(재시작 지점을 요청 시점에 고정) 후 수정 held-out 평가.
- **증상**: hang 시나리오에서 Agent도, 그냥 재시작도 **0/2**. Agent의 판단(설정 변경 없이 재시작)은 맞았다(의미 보존 2/2).
- **원인 분석**: 재시작한 job의 로그 → "Resumed from checkpoint at step 40" 후 **step 60에서 또 멈춤**. 시뮬레이터는 "step 60에서 멈춘다"고 고정돼 있어서, 60 이전 체크포인트부터 재시작하면 같은 자리에서 다시 멈췄다. 17번 전에는 SIGTERM이 step 60에 저장한 체크포인트로 재시작해서 우연히 가려져 있었다.
- **해결**: hang은 **일시적 장애**(데드락, 파일시스템 멈춤)를 흉내 내므로, 재시작한 job에서는 다시 일으키지 않게 시뮬레이터를 고쳤다. Agent가 아니라 채점 환경을 고친 것이라 held-out 규칙(결과 보고 Agent 고치지 않기)에 해당하지 않는다.
- **교훈**: 시스템의 한 부분(재시작 지점 고정)을 바꾸면 **시뮬레이터의 가정**이 깨질 수 있다. 두 방법이 똑같이 0점이면 방법보다 환경을 먼저 의심한다.

## 19. 수정 held-out 결과: Agent 8/10 vs 그냥 재시작 2/10

- **조건**: 개발 중 한 번도 돌리지 않은 7개 job (다른 lr·batch·시점·속도·체크포인트 간격·shard 구성, grad_accum 2로는 부족한 OOM, 종료만 해야 하는 job, 건드리면 안 되는 느린 job).
- **결과 (2회)**:

  | | 좋은 수정 | 정상 job 건드림 |
  |---|---|---|
  | Agent | **8/10** | 0/4 |
  | 그냥 재시작 | 2/10 (hang만) | 0/4 |

  설정이 원인인 실패(발산·OOM·손상 shard)는 **6/6** — 발산 전 체크포인트(240), 충분한 grad_accum(4, 1024), 손상된 5번만 제외. dev에서 코드로 옮긴 규칙과 도구 개선이 처음 보는 숫자에서도 통했다.
- **Agent가 틀린 2개 (고치지 않고 기록만)**:
  - hang 1회를 `healthy`로: 근거에 "log_age_vs_interval 13.3"을 **스스로 적어 놓고** "최근 로그들이 정상적으로 기록되고 있음"이라고 결론 → 근거와 결론이 모순.
  - 종료 중 멈춤 1회를 `finished`로: "Shutting down environment..." 뒤에 프로세스가 살아 있는데 끝난 것으로 판단 (dev 평가에서도 한 번 나왔던 실수).
  - 공통점: **마지막 로그 줄들이 정상이면 "지금 조용하다"는 신호를 가볍게 본다** (5번과 같은 계열).
- **고친다면 (다음 dev 작업)**: 프롬프트가 아니라 코드로 — "프로세스 생존 + 평소 간격의 10배 이상 침묵"인 job을 보고서가 `healthy`/`finished`로 쓰면 근거 대조처럼 거부 사유를 돌려준다(일관성 검사). 그 뒤에는 새 held-out이 필요하다.

## 20. memory ablation 1차: 숫자는 좋아 보였지만 믿을 수 없었다 (critic 오판)

- **상황**: runbook 메모리(실행 후 결과가 확인된 조치만 저장 → 비슷한 장애에서 검색) 구현 후 memory off/on × 3 에피소드.
- **겉보기 결과**: 해결 off 3/6 → on 6/6, 평균 라운드 2.67 → 2.17, 비용 −14%. 발표하기 좋은 숫자.
- **그런데 저장된 runbook을 열어 보니**: OOM 수정 runbook이 **성공 0 / 실패 3**. 실제로는 그중 여러 번이 끝까지 돌았다.
- **원인 분석**: 결과 판정(critic)이 "살아 있는데 평소 로그 간격의 10배 넘게 조용하면 멈춤"을 썼다. grad_accum을 늘려 재시작한 job은 step이 수십 배 느려지는데, **재시작 전의 빠른 간격**과 비교해서 "다시 멈춤 = 실패"로 기록했다. 평가 스크립트의 "결과 대기"도 같은 함수를 써서 일찍 대기를 끝냈다 → off 조건의 OOM "실패"도 일부는 평가 오류. (2번·5번과 같은 "느림 ≠ 멈춤" 문제가 critic에서 다시 나옴)
- **해결**: 멈춤 판정을 "지금 실행 구간의 예상 로그 간격 = max(최근 간격, 마지막 step_time × log_every)"의 10배로 바꿈. 재시작 직후 로그가 없으면 60초 대기. 테스트로 고정.
- **교훈**: 메모리는 critic이 정확할 때만 의미가 있다. Voyager에서도 critic이 틀리면 잘못된 skill이 쌓인다. **좋아 보이는 숫자일수록 저장된 내용을 직접 열어 본다.**

## 21. 기억은 있었는데 쓰지 않았다 (정책 문장 vs 메모리)

- **같은 1차 실행에서**: shard 멈춤 runbook에 "같은 설정 재시작: 실패 3 / 성공 0", "멈춘 shard 제외: 성공 3"이 쌓였는데, 에피소드 2·3의 첫 라운드에서 Agent는 **또 같은 설정으로 재시작**했다. find_runbooks는 매 라운드 호출했다.
- **원인**: 프롬프트 정책에 "hung → 보통 일시적이므로 변경 없이 재시작. 단 이 job이 이미 같은 설정으로 재시작했는데 또 멈췄다면 고쳐라"가 있다. 지금 job은 처음 멈춘 것이므로 정책상 "변경 없이"가 맞다 → **명시적인 정책 문장이 메모리보다 이겼다**.
- **해결 (구조로)**: 검증 단계에서 "거의 같은 장애(서명 유사도 ≥ 0.8)에서 이 종류의 조치가 2번 이상 실패하고 한 번도 성공 못 했으면 거부 + 성공 기록이 있는 방법을 알려 줌". memory off면 runbook이 비어 있어 이 검사도 작동하지 않는다 → ablation 공정성 유지. 테스트로 고정.
- **교훈**: 메모리를 "참고하라"고만 하면 다른 지시와 충돌할 때 무시된다. 6·15번과 같은 원칙으로, 검증된 실패 기록은 **검증 단계의 규칙**으로 쓴다.

## 22. memory ablation 2차: critic은 고쳐졌고, memory 효과는 "보이지만 아직 증명은 못 함"

- **조건**: 20·21번 수정 후 같은 seed(같은 shard 번호·batch 순서)로 memory off/on × 3 에피소드.
- **결과**:

  | | 해결 (3라운드 안) | shard 멈춤 해결 라운드 (ep1, ep2, ep3) | OOM | 에피소드당 비용 |
  |---|---|---|---|---|
  | memory off | 5/6 | R2, **실패**, R2 | R1 ×3 | $0.036 |
  | memory on | 6/6 | R2, **R1**, R3 | R1 ×3 | $0.029 (−21%) |

- **좋아진 것**: critic이 정확해졌다 — OOM runbook이 1차의 "성공 0 / 실패 3"에서 **성공 3 / 실패 0**. memory on ep2에서 **처음으로 shard 멈춤을 첫 라운드에 해결**(지난 에피소드에서 배운 "멈춘 shard 제외"를 다른 shard 번호에 적용).
- **아직 안 되는 것**: memory on ep3에서는 다시 "같은 설정 재시작"부터 했다. 그 시점 실패 기록이 1번뿐이라 21번 검증 규칙(실패 ≥ 2)이 작동하지 않았고, Agent는 성공 기록(1번)을 참고만 하고 정책을 따랐다. off ep2는 3라운드 내내 같은 설정으로 재시작해서 실패.
- **판단**: 해결률·비용은 on이 낫지만 에피소드 3개, 조건당 shard 사례 3개로는 **우연과 구분이 안 된다**. 지금 말할 수 있는 건 "critic을 고친 뒤 memory가 의도대로 쌓이고, 쓰였을 때는 첫 라운드에 해결한다"까지.
- **다음 조치 후보**: ① 에피소드를 늘려(예: 8개, seed 여러 개) 통계적으로 보기 ② 검증 규칙을 "실패 1번 + 같은 장애에서 다른 방법의 성공 기록이 있음"으로 완화 (이 결과를 보고 바꾸는 것이므로, 바꾼 뒤 새 seed로 다시 잰다).
- **교훈**: ablation은 **n이 작으면 결론을 내리지 않는다**. 논문에서 seed 3개로 1점 차이를 주장하지 않는 것과 같다.

## 23. 평가가 서버 디스크를 꽉 채웠다 (체크포인트 보관 정책 없음)

- **상황**: memory ablation을 크게(seed 2개 × 8 에피소드, GPU 2개 동시) 돌리던 중 두 실행이 모두 중단됐다.
- **증상**: 서버 루트 디스크 여유 공간 **105GB → 0MB**. 명령 출력조차 저장이 안 돼 원인을 바로 볼 수도 없었다.
- **원인**: "망가지기 전 체크포인트로 되돌아가기" 기능 때문에 체크포인트를 **step마다 전부** 남겼다(개당 약 21MB). 오래 도는 정상 job 하나가 수백 개(수 GB)를 만들었고, 평가 실행 폴더가 누적되며 약 100GB가 됐다. 평가가 끝나도 지우지 않았다.
- **조치**: 평가 프로세스를 멈추고, 사용자 승인을 받은 뒤 평가용 체크포인트 파일만 삭제(98GB 회수). 그리고:
  - 시뮬레이터에 **보관 정책**: 최근 5개 + 100 step 배수("이정표")만 남긴다. 최근 것만 남기면 안 된다 — loss가 망가진 지 오래된 job은 최근 체크포인트가 전부 망가져 있어 되돌아갈 곳이 없다 (13번과 연결).
  - 평가 스크립트 3개 모두, 채점이 끝난 실행의 체크포인트를 바로 지운다.
- **교훈**: 공유 GPU 서버에서는 Agent가 **자원을 소모하는 쪽**이 될 수도 있다. 장애를 고치는 도구가 장애(디스크 풀)를 만들 뻔했다. 실제 운영 Agent라면 "디스크 사용량"도 감시 대상과 안전장치에 들어가야 한다. 그리고 보관 정책은 기능 요구(되돌아갈 지점)와 같이 설계해야 한다.

## 24. 큰 ablation: memory 효과가 신뢰구간 밖으로 나왔다 — 그리고 그 한계

- **조건**: 22번과 같은 시스템(코드 변경 없음, 23번 디스크 수정만), **새 seed 2개 × 8 에피소드 × memory off/on**. 같은 seed·에피소드면 두 조건이 같은 장애(같은 shard 번호, 같은 batch)를 본다 → 짝 비교. 해결 못 함 = 4라운드.
- **결과**:

  | | shard 멈춤: 1라운드 해결 (ep2 이후) | shard 멈춤: 평균 라운드 | OOM | 에피소드당 비용 | 정상 job 건드림 |
  |---|---|---|---|---|---|
  | memory off | **0/14** | 2.44 | 1라운드 16/16 | $0.037 | 0/16 |
  | memory on | **12/14** | 1.38 | 1라운드 16/16 | $0.023 (−39%) | 0/16 |

  - shard 멈춤 짝 16개: on이 빠름 13, 같음 2, 느림 1. 평균 차이 **+1.06라운드, 95% CI [+0.62, +1.44]** → 0을 포함하지 않는다.
  - 학습 곡선(전체 job 평균 라운드): off는 1.5~2.0에서 그대로, on은 1.75 → 1.50 → 1.25 → **ep4부터 1.00**.
- **해석**: memory off는 16번 중 한 번도 첫 라운드에 못 풀었다 — 매번 "처음 멈춘 job은 같은 설정으로 재시작"이라는 합리적인 기본값을 따르다 1라운드를 버렸다. memory on은 앞 에피소드에서 "같은 설정 재시작은 실패, 멈춘 shard 제외는 성공"을 기록하고, **다른 shard 번호**에 그 관계를 적용했다.
- **한계 (발표할 때 같이 말할 것)**:
  - 효과가 난 건 **경험 없이는 첫 시도에 맞히기 어려운 장애 1종**(재시작해도 같은 자리에서 멈춤)이다. 로그만으로 고칠 수 있는 OOM은 차이 0 — memory가 모든 장애를 좋게 만드는 게 아니다.
  - 그 장애 유형은 내가 설계했다. "기억이 필요한 상황"을 일부러 만든 것이므로, 실제 서버에서 이런 반복 장애가 얼마나 흔한지는 별개 문제다.
  - 시뮬레이터, 모델 1개(gpt-5-mini), seed 2개.
- **교훈**: n=3(22번)에서는 "우연과 구분 안 됨", n=16 짝 비교에서는 구간이 0에서 떨어졌다. **같은 효과도 표본 크기에 따라 주장할 수 있는 말이 달라진다.** 효과를 주장할 때는 효과가 없는 조건(OOM)도 같이 보여 준다.

## 25. 컨테이너에서 승인했더니 종료가 안 됐다 (Docker AppArmor)

- **상황**: 승인 API를 Docker 이미지로 묶고, 호스트에서 도는 hang job을 컨테이너 API로 승인·종료하는 스모크 테스트.
- **증상**: job 조회(`/jobs`)는 정상(`alive: true`, 20배 침묵), 그런데 승인하자 **500 Internal Server Error**, job은 그대로 살아 있음.
- **원인 찾기**: 컨테이너 로그 → `jobs.terminate`의 `os.kill`에서 `PermissionError`. 컨테이너는 `--pid=host`(호스트 프로세스 보기)와 `--user`(같은 사용자, root 아님)로 띄웠으니 리눅스 권한상으로는 신호를 보낼 수 있어야 했다. 막은 건 Docker 기본 **AppArmor 프로필**: 컨테이너 밖 프로세스로의 신호 전송을 금지한다. `/proc` 읽기는 허용이라 조회만 됐던 것.
- **해결**:
  - 실행 단계의 OS 오류(권한 등)를 잡아서 500 대신 `failed` + 이유를 남긴다 (17번과 같은 원칙). 테스트로 고정.
  - 데모 실행 옵션에 `--security-opt apparmor=unconfined`를 명시하고, 이게 보안을 낮추는 선택이라는 걸 Dockerfile·README에 적었다. 운영이라면 필요한 신호만 허용하는 전용 AppArmor 프로필이 맞다.
- **교훈**: "학습 job을 죽일 수 있는 컨테이너"는 그 자체로 위험한 권한이다. 권한을 하나씩(`--pid=host`, 같은 사용자, AppArmor 예외) 열 때마다 무엇을 허용하는지 적어 둔다. 그리고 root로 돌리지 않았기 때문에, 이 컨테이너는 그 사용자의 job 말고 다른 프로세스는 종료할 수 없다.

## 이전 학습 프로젝트(agent-study)에서

- **문서를 안 읽고 "문서에 따르면"** (출처 지어내기): 키워드 채점은 통과, 도구 호출 채점이 잡음 → system 프롬프트로 1/3 → 3/3, 대신 질문당 비용 +24%.
- **프롬프트 수정 후 회귀**: "문서는 반드시 read_file로 읽어라"를 넣자 일반 상식 질문에도 문서 검색 (0/3) → 전체 회귀 평가로 발견.
- **LLM-as-judge의 실수 대부분은 루브릭의 구멍**: "모순 없으면 correct" → 지어낸 내용이 통과. 고쳤더니 문서에 있는 참인 정보까지 감점 → judge에게 요약된 정답 대신 **원본 문서**를 줘서 해결. judge 검증 세트에 그 경우가 없어 30/30이 나왔던 것도 발견 (검증 세트가 실제 실패를 대표해야 함).
- **LLM의 거절은 확률적**: 같은 공격에도 1/3은 실제로 위험한 도구 호출 → 방어는 코드에서, pytest로 보장.
